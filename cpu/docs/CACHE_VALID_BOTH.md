# I/D缓存有效位共同提前采样

## 实验范围

在144 MHz、种子1、PG2L200H-6FBB676上与按ready采样D-cache有效位的父工程对照。规范源experiments/cache_valid_both/rv32_cache.sv，SHA-256 73C8223AF99A8838567E837D41CCABB9AE9DFF93F395A2BB0132DFC51C7480AD。隔离工程build/cache-valid-both-stage，生产RTL不变。

唯一RTL变化是将原本只在D-cache生成的两个有效位采样寄存器同样用于I-cache，移除I-cache直接读取有效位数组的分支。标签和数据RAM、LRU、握手、回填状态机、计数器及CPU均不改，不增加流水拍。req_ready时采样实时组号，成功回填末拍仅更新victim对应位，其余忙态保持；无效请求窗口也遵守原有ready采样约定。

来源核验要求20项物理输入只有缓存变化，CPU保持F02A7F259598E85E5F2B8344ACC21FB1F347E714310B9F3DDADA6C4D70D7183C。I-cache 512组、D-cache 64组、BTB 8位索引，其他参数与144 MHz父工程相同。

scripts/test_cache_valid_both.py完整10项、140.323秒通过。继续使用独立固定缓存参考，比较逐拍控制、有效位/脏位、响应、内存请求和训练后的LRU，并分别检查LOOKUP有效位等价及ready采样/忙态保持/成功末拍更新约定。

首次定向测试揭示两个测试问题：只读前递日志标记实际为SYNC_READ forwarded_way0，而不是forward0；原激励只在第1拍注入读错误，漏掉仅末拍出错，因此去掉本拍r_error条件的反例未被拒绝。初次失败日志保留在build/cache-valid-both-readonly-focused.log。

为解决漏检，在共享测试类增加默认不变的transform_bench扩展点，仅本候选覆盖该扩展：清缓存后注入只有末拍出错的读事务，再执行正常重试并清缓存。候选与独立参考收到同一实际总线，原先的早期错误激励保留。修正后完整10项通过，未删掉漏检反例或放宽断言。

## 物理实现检查点

PDS构建20260908-032351-bec7a1f0终态失败：9483 LUT、5147 FF、WNS -1.212 ns，Some Constraints Violated。相对144 MHz父工程8749 LUT、5154 FF、+0.148 ns，多734 LUT、少7 FF，时序裕量减少1360 ps。相对8626 LUT完整基线也没有优势，不采用本候选、不升频、不启动其配对长测。

原生综合网表确认I/D各2个、合计4个GTP_DFF_C有效位寄存器，保持经D端逻辑实现，不是时钟门控；LRU仍是2个RAM256加1个RAM64，不能仅按RTL新增两位推算布局后的FF差值。

第一条路径从D-cache请求地址第4位，经标签RAM、hit1（扇出71）、CPU加载/地址逻辑和地址加法器，到d_req_address第8位（扇出28），再进入D-cache有效位预读寄存器的D端逻辑。11级逻辑，逻辑2.361 ns、布线5.428 ns，布线占69.688%；最差前三条均止于D-cache预读寄存器。不能把I-cache改动后的全局布局恶化误称为D-cache源代码也被改了。

按缓存原生模块统计，I-cache LUT原语实例2429→3186、MUX原语207→411、DFF原语1179→1181；D-cache分别831→843、249→248、484→484。这是原生实例数，不等于布局报告的LUT面积。新增面积主要集中于I-cache，而替换路选择仍按保存的请求地址直接读valid数组，命中使用新采样位；网表N16的replacement[9]仍取自_N7448/_N7449/_N7958/_N7959选择树。这提示了重复有效位选择逻辑的下一步实验方向，不证明所有734 LUT增量都由一个表达式造成。

后续已实现LOOKUP替换路选择复用采样有效位：独立144 MHz候选为8639 LUT、5126 FF、WNS -0.765 ns，比本版少844 LUT但仍时序失败，不采用；功能、同源审计与反例通过。详见CACHE_VALID_REUSE.md，原失败记录保留。

部分Icarus运行对独立命名generate块给出Anachronistic提示；编译与功能测试正常，8种严格Verilator板级lint通过。当前保留已送入PDS的精确源码，不在实现过程中改写其快照。
