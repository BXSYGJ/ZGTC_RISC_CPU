## 改动与捕获时序

规范源experiments/cache_valid_pipeline/rv32_cache.sv，SHA-256 DC35ACAC2059CE1B4CACCCCB0E5CEF734CEBAD8B2B8A157D3804254575478B30；父缓存为A7F92CDF40D5611A2BBDC96C5F13610A2BA29DEAD0D3E14863E124FF6E32F749。相对父工程20项物理输入与18项短测编译输入只改变缓存，CPU仍为F02A7F259598E85E5F2B8344ACC21FB1F347E714310B9F3DDADA6C4D70D7183C。

仅在可写D-cache分支增加两个有效位寄存器。req_ready窗口按实时请求组号读取，忙时按保存的组号读取；下一LOOKUP拍以寄存后的有效位与原异步标签比较。I-cache有效位仍直接读取原数组，标签、数据RAM、状态机拍数、字节合并、LRU与响应协议保持原实现。

成功回填最后一拍同时把有效位置1并进入LOOKUP，普通同沿读会得到旧有效位，因此显式旁路本次成功提交的victim有效位。只有r_valid、r_last、last_beat均成立且无本拍或累计错误才旁路。请求载荷仍遵守父工程req_ready时采样的约定，不改成只有req_valid才读取。

这两个预读寄存器不是所有状态下都与底层有效位数组完全同步：写回/填充命令或刷新改变有效位时，预读值可能短暂滞后。状态机不在这些阶段消费hit；本实验要求每次LOOKUP消费时与实际有效位一致，并通过真实事务、刷新、错误及重叠流验证。没有依靠滞后值发出响应，也没有将仅在LOOKUP成立的性质说成全状态不变量。

原生网表确实存在两个GTP_DFF_C预读寄存器，初始化0、CLK连接和lookup_valid输出经审计。最终全芯片FF却减少12个，是布局/优化的整体结果，不能用RTL新增两个寄存器直接推导物理总FF增量。

## 真实路径与后续

首条最差路径现在从D-cache同步数据输出，经加载字节提取及有效地址第9位，进入新增read_valid1寄存器的数据输入。7级逻辑，逻辑3.275 ns、布线3.285 ns，地址第9位在该路径上的扇出68。第二、三条仍从D-cache同步读输出进入D-cache状态控制。

这表明本版将部分查找工作移到请求侧后，形成了新的读数据至有效位预读路径，并未保证总延迟下降。不能只以寄存器后逻辑变少宣布优化成功，也不能仅看前三条路径就称其他路径已消失。
