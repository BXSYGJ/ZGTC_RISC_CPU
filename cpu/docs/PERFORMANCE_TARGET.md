## 不可只靠升频的差距

CoreMark/MHz = 迭代数 × 1000000 / 测量周期数。3.0要求每轮至多约333333.33周期；当前每轮1940533.878周期，还需约5.8216倍同频提升。

当前机器码每轮退休约752527.744条指令。若保持相同指令量且每拍至多退休一条，即使全部停顿归零，理想上界也只有约1.32885 CoreMark/MHz。要原样执行这些指令并达到3.0，平均IPC需要约2.25758，超过现有单发射/单退休架构。此推导仅针对该指令量和退休宽度，不是RV32I或其他编译器/架构的普适上限。

因此按以下顺序推进，而不是继续仅扫高频：

1. 固定RV32I兼容基线，首先用一致的O2/O3/Os编译选项比较退休指令量、代码尺寸与真实周期；所有上游算法文件保持不变，固件使用独立名称和哈希。不同编译结果不能送入同固件硬件消融工具。
2. 对实际计时区间做指令/函数及停顿归因，区分软件乘法、取指吞吐、load依赖、分支和Cache缺失；尚未取得此归因数据，不预先捏造瓶颈占比。
3. 改进连续取指/响应流水化、数据命中与前递，在独立差分和异常/中断测试保护下减少CPI，同时记录新增LUT/BRAM。不要将非标准运算替换或删减CoreMark工作量作为优化。
4. 编译选项筛选不足后，已依据退休热点实现默认关闭的标准M扩展，维持RV32I语义，并单独披露RV32IM编译及4 APM代价。更宽发射尚未实现；下一步优先减少现有单发射流水线的取指/数据/分支停顿。
5. 候选每次重新做120 MHz布局布线、长时性能/验证种子和重复实板测试；另保留最高闭合频率及CoreMark/LUT最佳候选，三者可能不是同一个配置。

## 自动门槛检查入口

在WSL Python中运行scripts/check_performance_target.py，传入--build与--uart，可选--json输出新文件。它复用严格的原始PDS/哈希/UART检查，固定要求120000000 Hz，使用整数不等式iterations × 1000000 >= 3 × cycles，避免四舍五入把略低于3.0判为通过。

退出码0仅表示该份证据通过数值门槛，2表示证据有效但目标未达成，1表示证据无效。JSON不会覆盖已有文件；包含三项实测指标、失败门槛与条件性的指令量上界。工具不证明板卡身份、全部电气约束或物理极限，必须结合原始UI租约与采集记录。

现有162 MHz和本次120 MHz实测均返回2，不能将此预期失败改为测试通过或掩盖。单元测试覆盖精确阈值、差一周期、错误频率、短时/验证种子、CRC、时序、器件、无效计数与条件上界；已接入validate.ps1。
