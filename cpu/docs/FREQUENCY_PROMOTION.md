# 达标后的升频接受规则

当前目标已提高到160 MHz，见FREQUENCY_TARGET_160.md；本文保留旧150 MHz阶段的过程与证据，不代表新版目标已完成。

## 两个阶段

第一阶段必须同时证明执行效率≥3.18 CoreMark/MHz、资源效率≥0.052 CoreMark/LUT、实际通过频率≥150 MHz。当前审计入口build/audit_timer_compare_split_seed2.py的--require-target要求真实双种子完整结果和各自PDS来源绑定，不把“输入检查通过”“时序通过”或“完整测试结束”单独视为三项达标。--inputs-only不能与任何资格开关组合以绕过门禁。

只有第一阶段的本地完整证据通过后，才冻结该版本作为后续优化的本地接受基线。实板验证是另一项必须明确完成的证据，不能由本地PDS或RTL结果代替。

第二阶段每次比较的是上一已接受版本，而非更早、更低的初始版本。新候选必须同时满足：

1. 仍满足第一阶段三个下限。
2. 实际通过的频率严格提高。
3. CoreMark/MHz不低于上一已接受版本。
4. CoreMark/LUT不低于上一已接受版本。

即使新版本仍高于0.052下限，也不允许以资源效率下降换取升频。即使显示到小数点后六位完全相同，也不允许隐藏执行周期增加造成的效率下降。更高时序报告估计频率不是已通过的新时钟；既有固件也不能重标为新频率。

## 精确数值门禁

scripts/frequency_promotion.py用不可变的正整数测量对象与有理数进行比较：执行效率由迭代数与实际周期计算，资源效率由实际频率、周期和该实现的LUT数计算。它只实施数值策略，不验证位流、源码、固件、时长或设备，不授予硬件/官方成绩资格；调用者必须先完成相应候选的真实来源审计。

scripts/test_frequency_promotion.py的8项方法0.002秒通过，包含60组独立有理数对照、等效率升频、一个周期的执行效率损失、一个LUT的资源效率损失、同频/降频拒绝、未达标基线拒绝、输入域及不可变性，以及相对上一接受版本而非旧初始版本的比较。

## 每轮证据

- 固定比较协议与CoreMark标准工作量，保留实际编译宏、工具链和上游来源。
- 每份固件绑定自己的实际PDS配置、PLL、时序、资源和位流。
- 两种6000轮运行各自CRC正确且实际建模计时至少10秒；保留原始UART、周期、退休数与缓存事件。
- 执行源码、物理与完整结果的拒绝控制，再调用数值策略。
- 未通过版本留在隔离工程并保存失败原因，不替换已接受基线；没有用户明确要求就不提交或推送GitHub。

有限实验不证明物理极限，不能把不确定性或尚未完成的实板、应用、稳定性、ILA、电气证据写成完成。
