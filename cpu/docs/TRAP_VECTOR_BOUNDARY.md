# 陷阱向量加法结果边界候选

## 实际根因与改动

上一字节比较候选的最差路径不是仅凭信号名猜测的PC加4。其实际原生网表 rv32_machine 中，源位置 rv32_machine.sv:43 的陷阱向量加法单元 N29_0_5 及后续 GTP_LUT6CARRY 已同时接入 mem_next_pc、mem_fault、mem_flush 和来自早期分支选择的 _N11913 等输入，输出直接变为 core/N1464，再驱动 next_pc。时序报告的 early_taken→N1464_8[6]→_N11913→machine/_N1005 等进位节点与该连接一致。因此，原工具实现把重定向选择合并到陷阱向量加法链中，使普通分支也出现穿越长进位链的静态路径。

候选 experiments/trap_vector_boundary/rv32_machine.sv 的SHA256为 18C05FC7BABCC027CBA1A3F477A8D9631E83A95A7EB7E07E280E5EFAE6D5D674。相对原machine 2949B5177E75069BEE3597E6025D37E31FBFBDE822997254040A728BE4EB00F9，仅将同一个陷阱目标加法表达式命名为带 syn_keep 的32位 trap_vector_sum，再由该网驱动 trap_target；不改变表达式、CSR行为、外设中断优先级、流水级或响应周期。

隔离工程为 build/trap-vector-boundary-stage，父工程为 early-compare-byte-stage。20份物理输入仅machine文件改变；核心、缓存、MMIO路由、PLL、固定固件与参数不变。父工程没有时序资格，不能继承通过结论；生产RTL不替换。

## 功能及执行周期

scripts/test_trap_vector_boundary.py 的3项方法1.677秒通过。对ENABLE_M=0/1，分别用原/新machine运行同一向量台架：每次147456项、共4次执行589824项。覆盖576个基址、全部四种写入mode、同步/中断原因以及32种低位cause，包含32位溢出、高位基址、无关cause高位；经过真实CSR写入验证mode归一化，而不是直接强制mtvec寄存器。每次含129024项直接目标、18432项向量目标、279项溢出，原/新输出与签名一致。这不是所有32位基址穷举。

原有machine台架在ENABLE_M两种配置下也做原/新4次运行，每次31项断言，包含CSR读写、计数器翻转/写优先、IRQ优先、陷阱保存及mret恢复。7个实际运行错误变体被明确目标值断言拒绝，涵盖偏移缺失/移位错误、缺失中断或向量模式条件、截断基址、错误cause高位及旁路sum；不把编译失败或超时算作有效拒绝。源码还原测试确认只有结果边界变化。

包含新machine的核心故障台架已重跑，2项方法0.956秒，24项场景与4个错误变体通过。8种严格板级lint通过。两次缓存CPU回归完整轨迹和最终内存与父工程相同；双10轮短测20260908-121222-aadf24f2与20260908-121235-bb7b62db仍为3151519/3156276周期、2748941/2749614条退休，CRC、缓存事件、参数与固件完全一致。来源和结果独立审计通过。短测只用于筛选，不提供完整成绩。

## 原生边界验证

本次实际综合网表中，machine再次具有独立的32位 trap_target 输出，而不是吸收PC重定向目标再输出 next_pc 的D输入。位2到31由30个连续的向量进位单元驱动，低两位是常零。进位单元的外部数据输入只来自mtvec、mem_cause的允许位和mem_exception，不再包含早期分支选择或mem_next_pc、mem_flush。

scripts/trap_vector_native.py 根据实际GTP单元及端口连接检查30个结果位、完整进位连接、零进位种子和低两位常零，并限制进位输入来源。它不靠某个任意网名出现就宣称隔离成功，也不宣称完整形式化等价。scripts/test_trap_vector_native.py 已对实际父网表拒绝、本次网表通过，并验证缺失结果位、重新接入early_taken、断开进位和丢失对齐位四类篡改；2项方法0.889秒通过。

该结果只证明综合连接实现了预期边界，不等于最终时序通过，更不等于上板通过。最终物理审计将绑定该检查器哈希、源快照、原生网表、完整Tcl、种子、PLL、固件和真实时序报告。

## 边界

本候选保留为已有物理改善但未合格的实验分支，不替换生产RTL。下一步可继续研究缓存返回到地址高位及MMIO接受控制路径，尤其区分整字和子字节load地址依赖；任何增加等待周期的做法都必须重新测量执行效率，不能用时钟提升掩盖CPI损失。只有最终时序合格，才执行同来源与固件绑定的完整计分。最新源码上板、应用/稳定性、ILA及电气证据仍需独立闭环。本轮不提交或推送GitHub。
