# 空闲状态清零除法余数

## 从失败路径到源码

MMIO载荷预采样第一阶段功能回归通过，但126 MHz WNS=-0.076 ns、135 MHz WNS=-0.282 ns，均拒绝上板，见 MMIO_PAYLOAD_QUALIFICATION.md。126 MHz 新最差路径由 Cache 数据、forwarded_b[8]、输入除数判零控制进入 remainder 的进位链。

已读取该实现真实 synthesize/pds_soc_top_syn.vm，而不是只按端点名称猜测：N251_17 对 req_operand_b[7:11]及[30]做 NOR，其余分组完成32位除数判零；N333_inv 同时受这些判零结果和请求/状态资格控制，并进入多个 remainder 位的 GTP_LUT6CARRY 输入 I3。原始连线、时序片段与文件哈希保存在 build/divider-input-path-analysis.json。

RTL中 remainder<=0 原本嵌在 IDLE、req_valid、除法操作且除数非零的分支内。这个有条件清零被综合吸收入余数算术路径，让尚未被接受的输入判零逻辑影响余数进位链。当前修订把清零改为仅由本地 state==IDLE 控制，不改变算术迭代本身。

## 正确性边界

- 接受任意非零除数的除法请求时，旧状态必为IDLE，所以余数仍在同一边沿归零，原除数/商绝对值和符号采样不变。
- DIVIDE中仍只按原试减逻辑更新余数，32次迭代和符号恢复阶段保持不变。
- 除零返回、乘法返回都不依赖空闲时的旧余数，不更改其结果和时延。
- RESPONSE等待接收期间不清除余数；取消/复位仍优先于正常状态机。
- 空闲时保存上次余数没有架构意义；现在允许无req_valid时清零，不代表无请求执行除法。

新muldiv源码SHA-256：F2553ABB4ACD0E480DA9372BF8BFD2F5C1BE71D66E61ED34C61A297C130396C8。

本候选叠加前一MMIO采样修改，相对已实板的126 MHz基线共两份RTL变化；相对失败的MMIO单改动候选仅改rv32_muldiv.sv。不能将双改动结果误报成对原实板源的单变量消融。

## 验证

既有muldiv_tb保留512组边界组合、2048组随机运算、取消/复位、输入变化和响应背压。新增默认关闭CHECK_IDLE_CLEAR，观察非零旧余数在无请求IDLE时确实清零，覆盖6466次清零检查、1150次非零旧值、3873次无请求；原有12544个检查全部通过。

新增除法精确延迟断言：非零除数在请求采样后的测试等待计数为33，除零为0；不是允许多等一拍再宣布功能相同。乘法原有0/1拍等待断言不变。

新增test_divider_idle_clear.py的三个反例：重新绑定请求/除数资格、破坏部分余数、提早一拍结束。分别被清零、算术和延迟断言拒绝，没有超时替代有意义的失败。恢复旧资格是优化结构保护，不代表旧算术实现不正确。既有乘法请求采样和MMIO反例同样通过。
