# 编译选项筛选与持续执行短测

2026-09-06。承接BTB_ADDRESS_BOUNDS.md的64项BTB、各2 KiB Cache、直接加载前递候选。此次不修改RTL，不替换已合格的120 MHz位流；所有新测试均为仿真，不能发布正式CoreMark成绩。

后续条件变化：独立8 KiB指令缓存/2 KiB数据缓存、256项BTB及写命中快路径配置下，链接松弛的十轮性能平均332611.6周期，优于同配置关闭松弛333871.7周期；对应4000轮性能/验证固件重新通过120 MHz实现。详见ASYMMETRIC_CACHE.md。下文较差结果只适用于当时的2 KiB对称配置，不外推为松弛在所有配置下都较差。

## 规则与实现范围

固定上游版本仍为1f483d5b8316753a742cbf5590caf5bd0a4e4777，构建继续检查该副本的版本与完整性。没有修改core_list_join.c、core_main.c、core_matrix.c、core_state.c或core_util.c，没有替换标准种子或算法。所有计分C源文件在同一编译命令下使用相同选项，实际参数通过Compiler flags串口行报告。规则见build/coremark-upstream/README.md。

- build_coremark.ps1和run_coremark_test.ps1新增LinkTimeOptimization开关，统一使用-flto，固件名增加_lto。默认关闭。
- 两脚本新增LinkerRelaxation开关，启用时链接参数为-Wl,--relax，固件名增加_relax；默认仍为-Wl,--no-relax。
- start.S原有gp初始化已经在.option push / .option norelax / .option pop之间；该保护保持不变，没有为了减少指令破坏全局指针初始化。
- run_coremark_test.ps1新增Iterations，限制1至10，默认仍为1；正式硬件长测继续使用build_coremark.ps1的长迭代选项。仿真看门狗仍有效，不能把10次短测当成10秒。
- 构建和运行清单记录LTO、链接松弛、串口延迟及迭代参数；运行前拒绝配置错配，拷贝后再次核对实际固件SHA-256，避免误用并行构建留下的最新清单或被覆盖的镜像。
- LTO/链接松弛非Profile运行也使用唯一时间戳与随机后缀，保存不可混淆的运行镜像和清单；现在日志明确打印运行清单文件名。
- LTO可内联或内部化iterate/stop_time，所以本轮LTO只使用CSR周期、退休数和Cache统计，没有伪造基于这些符号的函数画像，也没有禁用优化去制造可比较的profile。
- port的种子仍为volatile变量，CSR高低高读取保持volatile asm及memory clobber；没有改变计时函数或移出计时区的算法工作。

官方参考：`https://github.com/eembc/coremark`、`https://gcc.gnu.org/onlinedocs/gcc-10.2.0/gcc/Optimize-Options.html`、`https://sourceware.org/pipermail/binutils/2021-June/117126.html`。这些说明编译/链接机制与报告约束，不证明本工程的性能收益。

## 为什么不换成新选项

- O3 + unroll基线374184周期；直接加LTO变为394748周期，不能仅根据优化名更强就采用。
- 不展开的O3中，LTO把退休数296234减少到292998，却把周期386929增加到396518；I miss从1901增至3175。支持检查代码布局与取指压力，但不把全部差异都归因为Cache缺失。
- O3 + unroll启用链接松弛，退休数由276244降至274865，但周期增加到375958。指令更少不等于执行效率更高。
- 链接松弛对未展开的O3有小幅改善386929至386433，但仍未超过原O3 + unroll。
- 因此新开关均默认关闭，不为较慢的软件组合重复制作PDS候选，也不将别的RTL/容量的LUT数移用来包装这些组合的资源效率。原合格64项候选保持6935 LUT、4080 FF和120 MHz WNS +0.141 ns，证据仍以BTB_ADDRESS_BOUNDS.md的原位流为准。

## 持续执行短测

相同O3 + unroll、禁用LTO和链接松弛的硬件配置，以1、2、10次性能迭代和10次验证迭代检查重复工作：

10次性能平均为373566.3周期，比单次374184仅减少约0.16508%。不能将有限的重复运行结果外推为4000次实板测量；不同迭代固件也可能改变数据布局，不能把全部变化都归因为冷Cache。

按目标的周期预算计算，3.0 CoreMark/MHz要求每次迭代不超过1000000/3周期；相对本次10迭代平均，还需约10.76997%的周期下降。这是目标差距的数学比较，不是正式CoreMark分数，也不构成该时钟下硬件已达到或不能达到目标的证明。

## 回归与可追溯性

- test_coremark_run_contract.ps1使用PowerShell AST抽取实际运行脚本的保护条件，而不是另写一套同名比较器。14项检查覆盖有效配置、9个字段错配以及固件字节改变/无效哈希。
- CoreMark结果检查器15项测试通过；新开关的性能、验证及多迭代仿真均通过。默认控制镜像实际SHA-256仍为1037851449BD28133F1F8DA81D836C8832C4B30D0046A3CBFA94622A1BCCA202，与原单次候选完全相同。
- 最终集成回归build/validate-compiler-options-final.log通过，涵盖单元、CPU、参考轨迹、内存比对、lint、变异及新运行防护测试；不是新增实板验证。

每个运行的build/<RunName>.run.json、.hex、.uart和.result.json保留，启用Profile的运行额外保留符号和画像。完整运行名由相应日志中的清单行或上述唯一ID定位；旧LTO日志没有清单打印行的记录已按实际清单时间及固件名唯一匹配，并验证实际字节。

## 未完成与下一步

本轮没有新的实板或PDS性能候选，3.0 CoreMark/MHz和三指标物理极限继续未完成；ILA、独立GPIO输入、电气与SCBV等缺口不受编译选项测试影响。已排除本次有限编译选项能够填平缺口的猜测，而不是把更少退休指令或更小二进制直接当成达标。

已从当前RTL定位下一处具体控制开销：rv32_cache的fast_hit明确排除request_write，所以写命中即使已在LOOKUP沿完成存储更新，也必须经过RESPONSE状态才被CPU接收。后续可评估提前写命中响应，但必须保留写前响应数据、字节选通、零选通、反压时只写一次、写缺失/写回错误、同拍下一请求、维护与精确异常语义，并重新验证120 MHz，不能直接删除保护后宣布收益。该修改尚未实施。
