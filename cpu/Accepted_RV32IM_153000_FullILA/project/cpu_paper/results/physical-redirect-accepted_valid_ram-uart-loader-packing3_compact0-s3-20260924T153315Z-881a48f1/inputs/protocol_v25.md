# Protocol v25: Embench on the accepted 153 MHz hardware design

The reproduced CoreMark bitstream embeds its firmware in initialized RAM and has no demonstrated runtime loader. This experiment therefore builds new firmware-specific bitstreams from unchanged accepted RTL and constraints. They are derivatives of the accepted 153 MHz design, not the same bitstream or automatically the same resource/timing result.

Use the pinned 19 workloads plus the instrumentation dummy, unchanged upstream sources, RV32IM/ILP32, existing GCC 10.2 flags and libraries, 64 KiB memory, 16 KiB stack, heat 1 and scale 1. A separate board port waits for UART G before initialization/warm-up. It identifies the workload in START and FINISHED records and paces UART outside the timed interval. Preserve the two atomic cycle/retirement snapshots. Do not replace prior RTL results with the new board observations without identifying firmware and initialization differences.

Every board-bound image must have the full historical 42-data/33-trigger/1024-sample ILA mapping, GPIO, UART and caches; accepted fetch factoring, redirect priming and nominal 256-entry BTB remain fixed. Reuse the audited historical inserter/mapping procedure, verify input hashes, and independently audit each native PDS/ADS implementation at configured 153 MHz. Preserve timing failures. Do not program preliminary images without ILA as qualifying evidence.

Cold-program each qualified image, wait for actual programming confirmation, open UART at 115200 8N1 ASCII, wait for boot output to settle, then capture from before sending G until a unique matching FINISHED record. Preserve raw UI windows/chunks, observed padding, firmware/source/bitstream hashes, counters, CRC/verifier outcomes, CPI, native resources and timing. A capture failure requires a new attempt directory; never reset a failed receipt to appear fresh. Board identity is recorded explicitly; Experiment box 2 is a different board from historical box 1.

Check the new board port in RTL, including UART start gating and atomic-counter observations. Hardware reporting requires the actual verifier result for every workload. Compilation, timing closure or programming alone are not successful benchmark execution. Report raw counters and configured-clock-derived times, not an official normalized Embench score or independently measured frequency.
